## Vanilla behavior inspected

The original `PlayerScript.Update` door interaction uses its camera ray at 2.25 m, the native interaction eligibility gates, the `Door` tag, and `GetComponent<Door>()` on the exact hit object. E can start the native slow-open path; `Door.Update` owns the authored movement, rotation, `isOpen`, `opening`, `openingSlowly`, `canUse`, and progress state. `CarController.EnterVehicle` also runs the original driver entry and may call `Door.Use` on its native `car_door_L` or `car_door_R` as part of entry. These paths were inspected in the available `Assembly-CSharp.dll` decompilation, including `PlayerScript.Update`, `Door.Update`, `Door.Use`, `CarController.EnterVehicle`, and the native delayed door-close methods.

Previously, the world-door registry excluded every vehicle descendant. The vehicle adapter carried no door state, and the passenger prompt selected a car by proximity. Therefore a real door E press could be interpreted both by vanilla and by the multiplayer passenger prompt, while vehicle doors had no snapshot or live replication.

## Multiplayer changes and classifications

| Class | Intervention | Scope and preservation |
| --- | --- | --- |
| A | Register native `Door` components under the supported `VehiclesManager.firstCar` and `VehiclesManager.van` roots in the existing world registry. | Each identity uses its manager slot, relative native hierarchy path, and same-object component ordinal. Existing Door/Window snapshots and ordered state changes carry current `isOpen`, native motion flags, authored local pose, tags, enablement, and lock/broken state. Host samples while native motion is active at the existing 100 ms observation cadence; no vehicle-door motion stream or receiver-side hinge simulation is added. |
| A | Allow the existing Client `Door.Update` presentation boundary to consume Host motion for registered vehicle leaves. | Only the replicated door's native update is suppressed on the Client; the Host continues the original native update. Client interpolation follows Host local-position/rotation samples. Baselines apply silently; live updates retain existing door audio behavior. Scene invalidation and adapter teardown remove the session-scoped bindings and patches. |
| A | Replace proximity passenger selection with the actual native camera-ray hit on an open, settled, supported rear-side `Door`. Add that door reference only to `Passenger/Enter` seat requests. | The hit must have the native `Door` tag and component, be usable, and resolve to a registered rear-passenger door owned by the requested vehicle. Host validates the exact registered door, native open/settled state, authenticated actor eligibility, range, and line of sight. Front entry doors, trunk/hatch objects, storage access, and non-door targets do not qualify. Confirm/exit and driver requests carry no door target. |
| A | Consume the same E press used for passenger entry for that one `PlayerScript.Update` only. | The hook activates only after a valid open rear-door target is hit and the passenger seat is available. It temporarily clears `canInteract`, then restores it in a finalizer. Other native `PlayerScript.Update` work, the Player 1 first-person stack, and door E behavior on closed/not-settled doors remain in the original method. A failed request still consumes this one entry press, avoiding a simultaneous native close gesture. |
| A | Preserve Client native front-door close during original driver entry and report that outcome to Host. | Only `Door.Use` on the current cooperative driver's bound native front entry door passes through the Client authority hook. Host accepts the corresponding close only while that actor is pending/confirmed driver, the native leaf is open and enabled, and the authenticated actor can reach its collider. Host invokes native `Door.Use`; the Client suppresses the duplicate close sound when Host state arrives and restores the canonical Host state if the request is rejected. Offline and Host-side driver entry continue through original `CarController.EnterVehicle` and native door methods. |
| A | Require a registered native rear-side door before advertising multiplayer passenger capability. | The adapter scans actual `Door` components and enabled colliders under each supported vehicle, excludes the native front door fields, and checks their location against the existing rear-center passenger anchor. If no candidate passes, that vehicle's multiplayer passenger seat remains unavailable. This is session-scoped capability discovery; it adds no native collider, storage, seat, or persistence rule. |

The passenger-door geometry guard currently uses a 0.35–2.25 m lateral offset from the rear-center anchor, at most 1.5 m along the vehicle row axis, at most 1.25 m vertically, and at most 2.25 m collider clearance. These are fail-closed multiplayer classification bounds, not claimed vanilla measurements. The supported manager car/van geometry still needs a short in-game manifest check to confirm each actual rear door is included and no front/trunk leaf passes. The `Door` ray and action restrictions come from native source inspection; the exact live hierarchy could not be checked without a game session.

The Client puts the door identity in the request only after its actual native camera ray hits that object. The existing replicated pose contains position and body yaw, not camera pitch/direction, so Host independently verifies the registered rear-door/vehicle relationship, native open/settled state, authenticated eligibility, range, and line of sight; it cannot reconstruct the Client's complete camera ray from current telemetry.

## Verification and limits

Focused managed checks cover the required door reference for passenger entry, optional door wire round-trips, stable manager-slot/path identity, vehicle-owner matching, and rear-door classification exclusions. Existing registry tests cover ordered Door changes and authoritative snapshot application. The Release build succeeded, and the full existing multiplayer suite passed **799 checks**. The build emitted `NU1900` warnings because the offline environment could not query NuGet vulnerability metadata; there were no build errors. The guarded deployment installed 0.6.12.0 with DLL hashes matching the build, and the original game DLL/EXE fingerprints remained unchanged.

No game instance was opened. As a result, this work does not claim visual parity for native vehicle doors, that every supported model's door hierarchy passes the geometry bounds, a successful real Host/Client rear-door entry, or matching native open/slow-open/close animation and audio. Those require a controlled live Host/Client check with the first car and van. No NPC behavior, vehicle physics/handling, front passenger lootbox, storage capacity/ownership, economy, save rules, or original game binary was changed by this slice.
