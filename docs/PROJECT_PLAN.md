## Vision and acceptance philosophy
Two human players should eventually inhabit the same world and progress through the original game together. Either player may perform valid interactions and mission actions. Completed objectives and the associated world/progression consequences must be reflected correctly for both players. The mod should use original game controllers, animations, UI, NPCs, and missions where possible rather than approximating the original game with replacements.

Success requires actual in-game manual tests, not only successful compilation or plausible architecture. Some mechanics may be infeasible or need game-specific workarounds; report and prove limitations rather than promising full coverage early.

## Fixed decisions
- Two players initially; Windows PC; local testing with **two concurrently running game instances**.
- User reports that manual dual-instance launching already works; verify before changing that mechanism.
- Eventually deliver a small `TS2-Multiplayer-Launcher.exe`: **first invocation Host; second invocation Client**, automatically connecting to a local multiplayer session.
- The launcher handles the **mod session connection**, not Steam/third-party account authentication.
- Proposed authority model: **Host-authoritative**, subject to technical validation.
- Original systems first: gameplay hooks, character/NPC models, animation controllers, inventory/mission/vehicle systems if compatible.
- User manually tests every gameplay milestone. Logs, builds, static checks, and unit tests supplement—not replace—manual tests.
- Claude Code develops; Codex is called only for a targeted task explicitly approved by the user. No simultaneous editing.
- Token efficiency is mandatory: persistent navigational code map, targeted inspection, minimal dependencies, no automatic multi-agent review loop.
- **Permanent: original game code is preserved** (AGENTS.md "Permanent rules" §1). Runtime-only integration (BepInEx, narrowly scoped Harmony patches, original APIs/assets); no on-disk modification of game assemblies/assets without an established necessity and explicit user approval.
- **Permanent: mod performance is mandatory** (AGENTS.md §2, "Performance (permanent)" below). Only the mod's own overhead is optimized, never the original game's code.
- **User decision (recorded 2026-11-12, W3 prompt): both players will eventually share ONE cash balance and ONE bank balance.** Not implemented yet (W7 economy); balances are never merged automatically; storage / item transfers never depend on the separate balances.
- **Product target (recorded 2026-11-12):** a simple Host Game / Join Game menu; Player 2 loads straight into the host's cooperative world. The host-owned Player-2 record stays authoritative for Player 2's inventory (the client sandbox is never the durable owner).

## Confirmed multiplayer design (source of truth; updated 2026-11-10, M3.1.2: vehicle fleet)
Binding requirements. Items outside the current milestone are recorded, **not** implemented early.

**Session & authority.** One authoritative session controlled by the Host; one shared persistent world state (ultimately persisted in the Host's save). Clients propose; the Host validates, commits, acknowledges. State classes: session-wide shared, region-specific shared, player-specific, local presentation. Locally loaded Unity scenes never create divergent persistent histories.

**Shared progression.** Money, XP, mission progress, story progress, unlocks and rewards are shared. Either player can complete objectives; a mission completed by the Client completes for the Host and vice versa; both HUDs show updated objectives/progress; shared rewards and transactions are applied exactly once. Players may pursue objectives independently in different regions. Personal controls, cameras, positions and appropriate temporary states stay independent.

**Independent region travel.** Players enter regions independently; no forced teleport. Both see each other in the same compatible region when on foot (outside vehicles/hiding). The working M2 movement/animation system stays intact.

**Region time (M3.1).** Each gameplay region has its own authoritative time of day, owned by the Host regardless of where the Host is. A player entering an occupied/established region adopts that region's time (Host or Client). Players in the same region share one clock. Sleeping/advancing time (by Host or Client) changes only that region's clock. Unoccupied regions keep their last time. New regions initialize deterministically from session state. Travel never overwrites the destination's time with the traveller's previous time. Time corrections must not duplicate hourly/daily gameplay effects (rent, day/week, daily events, bank interest).

**SUPERSEDED twice — history:** (1) "exactly one shared player vehicle per region" (until M3.1.2); (2) **"shared fleet with several different player cars in one region" (M3.1.2–M4.1) is SUPERSEDED (2026-11-10, M4.1A)**. Do not implement multiple fleet cars per region. The M4.1 code (fleet registry, leases, snapshots, proxies) stays and is reused.

**Region vehicle rule (current, mandatory; M4.1A).** The two permanent player cars (Ranger `carNr` 0, Shadowhawk GT `carNr` 1) are globally unique. **At most one permanent player car is physically present and usable per region at any time.**
- A car never exists as two independently usable physical vehicles. Each car keeps its own identity, location and (future) inventory.
- A player entering a region that already has an assigned car adopts that car; the traveller's previous car is **not** brought along and stays in its previous region (Example B).
- Empty region: the first reservation the host commits decides the region's car. If two requests are genuinely tied (processed in the same host step), the host's own request wins; a committed reservation is never overridden later, including by the host. The loser arrives without a car; its car stays where it was (Example C). No artificial waiting periods.
- A car left in a region stays logically there (parked) until a player takes it elsewhere; no second copy is created (Example D).
- A joining client adopts the host's authoritative region/vehicle state; its own original auto-spawn must not create a second usable car (Example E).
- Both players in one region share that region's single car (driver + passenger, shared car inventory, safe enter/exit, travelling together, free movement on foot outside the car). Passenger support is deferred but the travel design must allow it.
- Hideout: the parked car objects act as **travel access points** even if the real car is elsewhere; they must not create an extra drivable car, duplicate inventory or move the real car unintentionally, and must not break the original garage/purchase interactions.
- NPC/world/stealable cars are outside this rule.

**Shared vehicle usage (future).** Exactly one driver per car; passenger seats verified in M4.1 (Ranger centre rear bench candidate `Female Sit Position`, Shadowhawk front passenger `Associate Sit`). Passenger camera follows the driver's camera **mode** (first person engine off / third person engine on) with its own correct local camera position. Travelling together brings both occupants.

**Travel and spawning (future).** Independent travel stays possible without a car (verified: the travel menu opens on foot at map borders, see CODEBASE_MAP §3.9). Never solve transport by duplicating a car. Joining an occupied region: safe spawn near the other player, else near the region car, else a verified original spawn; never inside walls, other players, occupied vehicles, moving traffic, below terrain or in scripted areas. Never teleport the other player when someone joins.

**Verified facts and design (M4.1/M4.1A audits):** vehicles CODEBASE_MAP §3.7; travel/placement §3.9; reservation, spawn and save design in PROGRESS "M4.1A". Key facts: the original travel always carries the current car to Madison/Hillville (the player arrives seated in it at the leave point nearest to where they left); the original save has one `CurrentCar`, one car position and one gas value; car storage is global → per-car location, region assignment and (later) per-car storage need host-owned mod state.

**Collision policy (M5.0, supersedes the ghost policy below):** a car presented on an instance that does not simulate it is the ORIGINAL scene object in kinematic observed mode, moved to the holder's poses in the physics step, solid in every state (parked, occupied, starting, driving); exactly one instance simulates (EVP paused on observers); damage/repair only where the local player sits (`CarController.OnCollisionEnter`, IL). The earlier "solid only while parked, ghost while moving" rule was an unacceptable compromise and is withdrawn.

**Collision / damage policy (M4.1 recommendation, historical):** repair money is charged at impact (`OnCollisionEnter`, ≤ $250). With one car per region, car-to-car collisions between the two fleet cars can only occur when a car enters an occupied region — which the region rule prevents; remaining cases (proxy vs. local player/NPC cars) stay Option C (no colliders) until passenger/driving handoff work needs more. Never globally disable damage or repair costs. **M4.2.2 update:** a non-simulated presentation is *solid only while parked and settled* (hideout: original frozen body colliders; elsewhere: kinematic shell of the cloned body colliders, untagged, default layer) and a *ghost* (colliders off) while driven/moving/travelling. Never physically authoritative; full synchronized car-to-car collision physics is not solved.

**M4.2 decisions (implemented, pending QA; details PROGRESS "M4.2").** Travel clicks from the original menu are decided by the host *before* the original save/reload (client click held, resumed exactly once on the grant; host decided in place); scripted transitions (arrest, heists, delivery, repairs) keep the original behaviour and never carry a car. A car has one region and one *holder* (the instance simulating it); the other instance renders a proxy. The car of a region stays with the player who stays; the hideout garage may store both cars and shows copies of cars parked elsewhere as frozen travel access points (plus an optional on-foot travel-menu key). Per-car fuel and parking pose live in host parking records and the host-only fleet file `%LOCALAPPDATA%\TS2MP\fleet-<profile>.dat` (profile = PlayerPrefs `Profile`). Heist/mission regions keep the original car behaviour (mission transport exempt; not synchronized).

**M4.2.1 decision (hideout travel proxy).** A *real* car (one id, one region, one holder simulating it with the original controller, authoritative fuel, future storage/seats) is separate from its *hideout travel proxy*: in the hideout every unlocked car the local instance does not simulate stays visible on its ORIGINAL scene object, physics frozen, CarBox / van door / heavy-cargo colliders disabled, and E (original `SitCar` interaction → `CarController.EnterVehicle`) opens the original travel menu (`PlayerScript.ShowTownSelection`) instead of entering. A proxy of a car that is physically home (`ParkedOther`) follows the holder's pose; a proxy of a car elsewhere (`AwayProxy`) keeps a hideout spot. Proxies are never fleet vehicles, never carried, never drivable, never grant a lease or storage. Presentation is derived only from the host's records (never from the local `CurrentCar`). Outside the hideout the other player's car stays a stripped visual (M4.1) until driver handoff/passengers. Future contract unchanged: either player can claim the free driver seat (host-validated lease, safe handoff), the other rides as passenger (Ranger centre rear `Female Sit Position` candidate, Shadowhawk `Associate Sit`, original Sitting animation), passenger camera follows the driver's camera mode (first person / `Set_TPP` third person) — not implemented yet.

**M4.2.2 decision (driver seat ≠ simulation authority).** Four separate concepts: persistent identity (the record, never deleted on exit), driver seat (`Driver`: empty / P1 / P2), simulation authority (`Holder`: the instance running the original physics; may stay with a player while the car is parked) and per-instance presentation. E on a car presented here but simulated by the other instance (`ParkedOther` in the hideout, `RemoteVisual` elsewhere) requests the free driver seat: client proposal `vehicleTake` / host in place → host validates (same fleet region, unlocked, not reserved, seat empty, requester drives nothing else, no handoff lock of the other player, car *settled* = no movement/driver reported by its holder for 1 s) → commits the freshest pose/fuel, then `Holder = requester` (5 s handoff lock) → the requester's reconcile makes the car Real and the intercepted original `CarController.EnterVehicle` is resumed exactly once → normal lease claim. Occupied seat → feedback only (future passenger interaction); away proxy → travel menu (unchanged). A car that stays behind when its holder travels is handed to the other player present at decision time.

**M4.2.3 travel ownership rules (supersede "the car of a region stays with the player who stays").** Intent = the host-committed driver lease at the decision (claimed from the original `is_sitting_inside`/`current_vehicle`; client lease/release share the travel request's ordered proposal sequence). **A** driver travels → the car is carried (reserved at the destination at decision time; old region loses it at once; staying player on foot), unless the destination is a one-car region that already has a car (region rule wins, the car stays). **B** on foot → the car stays (handed to the player who stays, if any; on foot alone the original carry rule still applies). **C** the other player drives → never carried, nothing reassigned. **D** a parked car's holder is no possession. **E** the hideout away proxy stays travel-only. The remote driver is shown seated (Codename model, original `Sitting` clip, car-specific anchor from the car's own seat transforms).

**M4.3 decision (passenger seat):** passenger = host-reserved seat (`vehicleRide`), separate from driver seat and simulation holder; local adapter built from the original door/trigger, the non-driver parts of `EnterVehicle`/`ExitCar`/`Set_TPP` and the companion seat `associateSitPos` (the original game has no second human seat); passenger camera follows the driver's camera MODE (record flag `Tpp`). Until Phase B, travel with a passenger aboard is refused visibly. Phase B = joint travel as a host transaction on top of `TravelDesk` (vehicle id, driver, passenger, source, destination, per-participant load state, idempotent commit, recovery to on-foot in the correct region). Remote engine audio from snapshots is a tracked quality requirement.

**M4.3 Phase B decision (2026-11-11, joint travel):** one host-coordinated logical transaction per journey (`jointTrip` registry entry: id, car, driver, passenger, origin, destination, phase, progress); the driver's original travel click is the only command and is decided as a normal M4.2 `Carry` (driver path unchanged); a passenger never chooses a destination. The passenger's instance runs its OWN original `GameManager.Select<Dest>()` only after the host saw the driver leave the origin (no move for a travel cancelled before departure), loads at its own speed and is re-seated through the established passenger seat path once the car is live at the destination (driver arrived, seated by the original `IsStartingCar`, simulating it). Host authority over the decision is separate from vehicle physics: the driver stays the holder in both roles. Joint travel only when the car can be carried (empty destination region; not to special destinations; CarBox closed; seat confirmed) — otherwise the click does nothing. Hideout/Auto Shop/Verwood: both arrive on foot, as the original driver does. Scene loads are not atomic across processes: rollback before the passenger departs, forward recovery (on foot, seat released) after it; timeouts 150 s / 30 s after arrival.

**M4.3.1 decision (passenger interaction, storage):** E resolution order = original target (via the original PlayerScript ray and tag branches) → seated passenger input → passenger request → nothing; passenger entry only next to the car (≤ 1.2 m from its box, ground level, body hit or facing + line of sight), never a global range or trigger volume. Car storage (`CarBox`) is per save and not networked; until a **host-authoritative shared car storage** milestone exists (item counts owned by the host, client storage UI driven by host state, validated insert/withdraw transactions, capacity, concurrency, disconnect, persistence), storage from a passenger seat is allowed only on the host and refused on the client. That milestone has its own QA boundary and also has to decide the pre-existing client access to its sandbox storage copy. Order after M4.3.1 QA: shared car storage (if approved) and/or Phase B joint travel — not both in one untested deployment.

**M4.3.3 hotfix decision (2026-11-11, user):** the host saves the cooperative session; Player 2 never needs a separate save. Player 2 keeps its own backpack/money/bank/tools as the host-owned record; a client report is committed only after the host wrote it durably; the client restores the record in every scene and synchronizes at every scene exit. The host world save keeps the original checkpoints.

**M4.3.3 decision (2026-11-11):** Player 2's inventory (backpack, money, bank, tool wear) is a host-owned record per host save profile, restored into the client and kept current by client reports; Player-2 CarBox transfers are host transactions written durably before acknowledgment, with a journal replayed against a watermark stored in the host save. The hideout locker, dropped-item recovery, the economy paths of the client's world (rent, world purchases, mission rewards) and world loot stay outside this record (explicit dependencies, see PROGRESS "M4.3.3").

**M4.3.2b finding (2026-11-11):** a correct client CarBox transfer requires a durable, host-owned Player-2 inventory (the client sandbox is re-seeded from the host save at every start). Open decision for the user/architect: schedule that inventory milestone before or after Phase B. Until then client storage is view-only (lease-exclusive, host contents).

**M4.3.2 gates (user/architect decision 2026-11-11):** M4.3.2a passenger UX (built, PENDING QA) → user QA → **M4.3.2b shared CarBox** (one host-owned storage, exclusive host-committed session lock with id/generation, timeout that never revokes an in-flight transfer, release on disconnect/exit/travel/shutdown; original storage UI on both instances; client insert/withdraw as host-validated idempotent transactions with recovery across both processes; the client never edits its stale sandbox copy; tested with backups) → user QA → **M4.3 Phase B joint travel** (driver + passenger travel as one host transaction on the existing travel continuations; seats, vehicle, camera modes kept; asymmetric load times, cancellation, disconnect/reconnect, late packets; CarBox session resolved before departure) → user QA. Shared CarBox and joint travel are mandatory, not optional. Remote engine audio and fleet persistence weaknesses remain tracked follow-ups.

**Vehicle sequence (M5.0, historical):** M5.0 foundation → user QA → **M5.1 passenger occupancy** (delivered as M4.3 Phase A) (host seat registry with entry/exit reservations keyed by vehicle id; Ranger centre rear `Female Sit Position`, Shadowhawk `Associate Sit` — both to be verified in game; passenger enters through the original door; passenger camera follows the driver's camera MODE with its own viewpoint) → M5.2 joint travel as a host transaction (car moves once, both seats kept, rollback on load failure) → persistence alignment with game save points → per-car storage.

**Vehicle sequence after M4.2.2 (historical):** **next vehicle milestone = passenger interaction + passenger camera synchronization** (Ranger centre rear `Female Sit Position`, Shadowhawk `Associate Sit`; passenger camera follows the driver's camera MODE with its own local viewpoint; identical with host or client driving; travelling together) → per-car storage → remaining persistence/edge cases. Earlier plan text "M4.3 shared driving / driver lease handoff" is delivered by M4.2.2 (pending QA).

**Police (future).** Shared police/NPC world; individual wanted levels and pursuit targets; detecting one player never flags the other automatically; both can be pursued if both are identified; a pursuit of their shared vehicle may affect both occupants; arresting one player never resets the session.

**Connectivity.** Keep the double-launcher localhost workflow. Later: Host/Join by direct IP and configurable UDP port (port forwarding allowed for Internet play), with session authentication and safe validation. No Steam Spacewar integration, no split-screen, no unnecessary central server. Authentication systems are never modified.

**Performance (permanent).** Every milestone minimizes CPU, memory/GC, network and rendering cost: no per-frame global object searches, cached references invalidated on scene reload, no per-frame allocations/logging in hot paths, cached accessors instead of repeated reflection, event-driven updates, bounded configurable send intervals, no broadcasting of unchanged state, compact packets, no duplicate simulation of authoritative effects. Player sync stays at 20 Hz unless evidence justifies a change. Performance claims require measurements. Each milestone report identifies the mod's changed hot paths, their measured cost where practical, network traffic and GC/memory behaviour, a comparison with the previous version when meaningful, and the potential FPS impact; FPS claims only from real in-game FPS measurements.

## Working networking principles (to validate)
- Stable IDs for replicated objects, players, missions, and events.
- Host validates and applies authoritative changes; clients request actions and render confirmed state.
- Reliable, replay-safe messages for inventory, mission, money, and world-state changes.
- High-frequency state (movement/vehicles) uses appropriate snapshots, smoothing/interpolation, and ownership handling.
- Prevent duplicate rewards and duplicated pickups; plan late join/reconnect and scene transition explicitly.
- **Do not assume the economy design:** shared mission/world progress is required; shared vs. separate player wallets/inventories remains a design decision after inspecting original mechanics.
- **Do not assume all original missions are replicated safely:** validate one real end-to-end mission path early.

## Milestone execution contract
- One prompt given by the external architect for one specific milestone.
- Claude works inside the authorized repo, performs evidence-based minimal implementation, and documents findings.
- Mandatory concise final report: changed files, real build results, verified facts, blockers, manual test checklist and outcomes.
- Human user tests where necessary and reports results/logs; architect checks and authorizes next milestone.
- No next milestone is started automatically.

## Risks to track
- Original single-player logic might assume one player, one camera, one save, one active mission owner.
- Shared local save directory could create conflicts when two processes run.
- Native Unity physics and animation are not automatically network deterministic.
- Existing mods can be outdated or have code/license restrictions.
- Two game instances on one PC may affect performance; remote multiplayer needs additional testing later (N1: internet play between two PCs built, not yet tested; latency/packet loss behaviour of the gameplay sync over WAN is unknown).
- Automatic multiplayer connection must not be confused with Steam credential automation.

## Open decisions (defer until supported by evidence)
- Game runtime and final mod loader configuration.
- Transport library and host discovery details. (N1: LiteNetLib UDP kept; discovery = the host tells the joiner address, port and join code; no matchmaking/relay. Transport encryption is open.)
- Shared wallet versus separate wallets; inventory ownership and reward distribution.
- Host save ownership and client-side save suppression/isolation strategy.
- Reconnection policy and handling of mission scenes/teleports.
